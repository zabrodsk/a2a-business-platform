Pneu007: using the agent payment setup

This is a Cardano Preprod demonstration. Payments use free test tokens with no monetary value. The reservation and service are fictional. The displayed CZK amounts are demo business records, not collected Czech crowns.

What the names mean

Cardano is the blockchain: a shared transaction ledger that records which address owns which tokens. ADA is its native currency; lovelace is the small unit, with 1 ADA equal to 1,000,000 lovelace. Preprod is a separate practice network. Its test-ADA cannot pay real bills or be treated as real money.

Blockfrost is the API connection used to read that ledger and submit signed transactions. Your project key identifies the API account. Masumi is the agent payment software: its buyer node sends the test deposit into an escrow, a smart contract that holds tokens until the agreed release conditions. Its seller node records the result and later collects the payment. The wallet recovery words, rather than the Blockfrost key, control the wallets.

The digital result here is a reservation receipt. Its hash is a short cryptographic fingerprint recorded on-chain, allowing the backend to check that the receipt has not changed. The full receipt stays in the application database.

What is free

The Masumi software, Blockfrost Starter access within its limits, and Preprod faucet tokens are free. The payment nodes use existing Mac mini resources. No additional Railway services or paid subscriptions were created for them. The existing website still uses its existing Railway billing plan; electricity, internet and AI account/model usage remain separate costs.

How an agent buys

  1. The customer agent creates its case and proposes a bounded mandate.
  2. The customer approves that mandate in the human account. Agent tokens cannot grant that approval.
  3. The business agent issues a stored quote. The customer agent accepts its exact version.
  4. The business agent runs checkout ORDER_ID through the garage client. The backend checks the quote, mandate, recipient, fixed SKU, asset quantity and wallet budget.
  5. Confirmed escrow funding creates one booking and a digital reservation receipt.
  6. The backend submits the receipt's hash to Cardano. After the escrow window, the seller node collects the payment.

The public payment configuration supplies seller_id and each registered SKU's agent_identifier so agents can construct a recipient-bound mandate without reading private node configuration. Give each agent only its assigned business/customer tool token. Keep node API keys, admin keys and wallet recovery words on the server.

Current test limits

Only deposit-500 is registered: 5 test-ADA, corresponding to the fictional 500 CZK deposit in the demo mapping. Unregistered full-payment variants are unavailable. The controlled buyer started with 20 test-ADA; the human checkout exposes a maximum additional budget of 15 test-ADA. That maximum is a spending ceiling, not the actual transaction fee.

The controlled smoke profile permits funding for 5 minutes, result submission by 16 minutes, seller collection eligibility after 32 minutes and external dispute timing at 48 minutes. The pinned node's collection scheduler adds another 10 minutes after unlock, so automatic collection normally starts around minute 42, followed by blockchain confirmation. These intervals satisfy the pinned protocol's minimum gaps. The ordinary profile remains 20/60/90/120 minutes, with the same collection scheduler buffer.

This demo supports one buyer payment workflow at a time until payout or refund completes. A confirmed booking does not mean the buyer wallet is available for another purchase. Local application purchases are intentionally disabled; the single Railway application owns the active buyer workflow.

Reading status and recovering

StatusMeaning
purchase_requestedRequested or queued; funding is not yet confirmed.
escrow_fundedFunds are confirmed in escrow; the booking can be confirmed.
result_submittedThe digital receipt's hash is on-chain; the collection window may still be pending.
seller_paidThe backend verified the confirmed withdrawal transaction, matching escrow input and actual seller collection output through Blockfrost.
refund_requested / refundedA request and an observed return of funds are separate stages.

After a network timeout, inspect the existing order and its payment ID. Do not create a second case or payment to retry an uncertain purchase. Owner recovery uses the original identifier. The live smoke driver persists its order before checkout and retries only read-only status lookups after interruptions.

npm run masumi:check inspects the local environment only; its local purchase flag is deliberately disabled. Use the public application's payment configuration to check the deployed setup. Configuration checks cannot themselves prove a blockchain payment; the live proof contains actual transaction references.

Private setup and proof JSON files live under ignored data/; wallet/admin secrets live in ignored environment files with owner-only permissions. Preserve those files and database volumes. After rotating the Blockfrost key, rerun node infra/masumi/provision.mjs, update Railway's server-only MASUMI_BLOCKFROST_PROJECT_ID, and recreate the nodes with the Compose file so stored RPC configuration and process settings agree.
