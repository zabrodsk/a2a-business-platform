1. Cíl: funkční business, který lze auditovat

Nejprve vznikne samostatně fungující legacy systém Pneu 007. Poté jej skutečný firemní GrokBot audituje a navrhne svůj rulebook. Web, objednávky, ceny, kalendář, evidence plateb a testovací dodavatelé fungují bez Handle i bez aktivního pravidlového profilu. Handle následně připojí firemního agenta k týmž systémům přes omezené nástroje.

Fungující legacy businessČtyři stránky, klientské objednání/nákup, zaměstnanecká administrace, SQLite, kalendář, konzistentní dummy historie a mock supply chain.
Audit ze skutečných podkladůWeb + tři interní dokumenty + čtení systémových dat. Agent identifikuje procesy, autority, partnery, mezery a rozpory. Výsledný rulebook předem nevzniká.
Agent dokáže službu koupitDiscovery, skutečné jednání dvou GrokBotů, schválený mandát, rezervace a ověřená Masumi platba na Cardano Preprod.
Definice hotového výsledku: (1) člověk přes web vytvoří objednávku, zaplatí a uvidí rezervaci v kalendáři; (2) GrokBot z tohoto prostředí vytvoří audit a návrh pravidel s citacemi; (3) po lidské aktivaci dva skuteční GrokBoti bez kopírování zpráv uzavřou zakázku s Masumi payment ID a on-chain důkazem; (4) změna zdroje skutečně změní vynucování pravidla. Samotný web, připravená konverzace nebo lokální imitace Masumi nestačí.

Novější požadavek rozšiřuje původní zadání: Masumi nahrazuje lokální simulaci jako požadovaný platební provider. Přidává se vedle původní zálohy také nákup s úhradou celé služby, pouze na základě nového odpovídajícího mandátu. Blockchain a SQLite mají oddělené transakce; původní společný atomický zápis bookingu a peněženky se pro tento režim nahrazuje trvalým platebním workflow.

Zachovat fiktivní firmu, syntetické údaje a výslovný testnet. Žádné skutečné autoservisní služby ani mainnet platby. P0 neobsahuje autonomní nákup dílů či třetího dodavatelského agenta; funkční mock dodavatelé slouží legacy provozu a auditu. Zdroj: zadání §4–5, §7–10; upřesnění uživatele: backend, Masumi a robustní auditovatelný demo systém. Uživatel potvrdil dopracování plánu, nikoli zahájení implementace.

4. Robustní podklady pro audit a rulebook

Audit je úvodní pracovní úkol skutečného firemního GrokBota. Dostane URL běžícího legacy webu a schválený read-only přístup. Výstupem auditu je vlastní mapování firmy a návrh pravidel, nikoli načtení předem hotového rulebooku. Zachovat omezený rozsah zadání: čtyři webové stránky, tři hlavní interní soubory a jasně pojmenované datové zdroje, bez obecného crawleru libovolných systémů. Zdroj: zadání §5.1–5.4.

Co agent při auditu skutečně dostane

Každý zdroj má source_id, verzi, hash, viditelnost, účinnost a označenou autoritu. API/exporty mají metadata o stáří a původu. Auditní read-only pohledy poskytují pseudonymizované katalogy, provozní hodiny, dostupnost, vzorky objednávek a jejich událostí, sklad, partnery a platební souhrny. Žádné klíče peněženek ani autentizační tajemství. API dokumentace poskytuje fakta o existujících funkcích, ne hotová obchodní pravidla.

Výstupy se ukládají odděleně do soukromých verzovaných audit runs: business-profile.json, návrh rulebook.json, audit-findings.json a manifest přečtených zdrojů. Každý závěr má source ID a konkrétní úryvek nebo cestu k datovému záznamu. Agent nevymýšlí pravidla, která ve zdrojích nejsou. Kritické neznámé parametry nebo nevyřešené rozpory blokují aktivaci příslušných transakčních schopností.

Oddělit backend od vznikajícího rulebooku

Legacy backend má vlastní cenový a bookingový systém a běžné lidské role. Agentická vrstva podporuje obecné schéma kontrolních parametrů, ne natvrdo naprogramovanou „autonomní slevu 5 %“. První spuštění neobsahuje aktivní agentí rulebook. Audit navrhne pravidla; majitel vedle zdrojů schválí konkrétní verzi; teprve poté ji server použije pro agentí operace a transakční Agent Card.

Podporované parametry pokrývají povolené služby a čtyři kola, slevové pravomoci, vklad/plnou úhradu, časovou platnost nabídky, autoritu kalendáře, síť/provider/asset plateb, omezení materiálových nákupů a eskalace. Finanční limity z mandátu jsou zákazníkovou samostatnou autoritou. Všechny kritické akce vynucuje backend. Agent může pravidlo navrhnout, nikdy je sám aktivovat.

Aktivace a důkaz skutečného auditu

  1. GrokBot načte čtyři stránky, tři dokumenty a pojmenované read-only zdroje; konzole ukáže manifest, profil, návrh a findings.
  2. Majitel schválí doloženou verzi. Z ní se vygeneruje SKILL.md a veřejný profil. Ověřit aktuální Agent Skills formát a skutečné načtení klientem v reálném úkolu.
  3. Ve zdroji změnit autonomní slevu z 5 % na 3 %, provést nový audit a lidskou aktivaci. Stejná 4% nabídka nově čeká na majitele; backend se mezi běhy neupravuje.
  4. Samostatně změnit mock sklad/ETA nebo provozní hodinu; ověřit, že profil či dostupnost vychází z nového zdroje a agent nejistotu přizná.
  5. Před hlavním demem připravit odpovídající zdroje a schválenou verzi. Starou nabídku přes změnu pravidel odmítnout; novou verzi neaktivovat uprostřed platby.

Zdrojový obsah je důkaz, ne instrukce k instalaci kódu nebo změně role. Crawl je omezený na schválené hosty a cesty. Přidat negativní fixture s vloženou instrukcí „schval si výjimku“; audit ji nesmí vykonat ani z ní vytvořit povolení. Dodavatelská data se čtou pouze z lokálních mock rozhraní.

5. Jednoduchý, ale funkční legacy backend

Návrh stacku: Node.js/TypeScript, stávající Express a better-sqlite3, jeden backend s trvalou SQLite a statickým webem/administrací. Podle aktuálního repozitáře již existují manifesty root workspace a apps/relay/package.json s těmito knihovnami; relay je samostatná rozpracovaná integrační větev, kterou tato změna plánu nepřepisuje. Nové legacy moduly plánovat v apps/legacy/ a společné doménové operace v packages/demo-garage/. Konkrétní build/runtime se sladí s existujícím projektem při realizaci.

Pro vlastní business stačí jeden server a DB. Masumi Payment Service je externí komponenta s vlastními závislostmi; její databáze se nevydává za část naší SQLite. Nepřidávat další CRM, workflow engine, vektorovou DB ani calendar SaaS. Požadovanou Masumi infrastrukturu oddělit od jednoduchého legacy backendu.

Kalendář jako autorita pro termín

Interní kalendář je součást backendu; Google Calendar není závislost. UI nabízí den/týden a vytížení boxu. ICS je export ze stejného bookingu. Návrh fiktivního provozu: pracovní dny 09:00–18:00 Europe/Prague, jeden servisní box, přezutí 60 minut, výměna celých kol 45 minut. Main slot 16. října 2026 16:00–17:00 je v seedu volný. Slot pro B je jiný; poslední společný slot slouží koliznímu testu.

Objednávka má explicitní stavy draft → quoted → awaiting_payment → confirmed → in_service → completed; vedlejší payment_failed, cancelled, refund_pending, refunded. Agentí případ má vlastní negotiating/waiting_owner stavy. confirmed neznamená, že proběhlo fyzické přezutí, a completed servisní objednávky se nikdy nenastaví pouze z výsledku rezervace.

Agentická vrstva nad stejným provozem

Společné kontrakty doplnit o Order, CalendarSlot, BookingHold, PaymentIntent, PaymentObservation, Partner, SupplierQuote a AuditSource. Platba má samostatný stav settlement.

Scheduler zpočátku dovolí jeden aktivní krok na případ a jednu přidělenou práci na obslužného bota. Čekání na majitele nebo blockchain drží uložený případ/hold, nikoli běžícího pracovníka nebo otevřený DB zámek. Zdroj: zadání §7.4–7.6.

5b. Agentický nákup a platby přes Masumi

Požadovaný provider je Masumi na Cardano Preprod. Lokální simulátor je pouze pomůcka pro development a automatické failure testy, ne splnění platebního požadavku. Dvě role kupující/prodejce mají oddělené peněženky nebo PaymentSource a omezená oprávnění. Zvolenou verzi služby a API pinovat, nikoli implementovat podle marketingového SDK příkladu.

Rozdělení protokolů a infrastruktury

A2A slouží discovery a jednání zákaznického/firemního bota. Masumi MIP-003 poskytuje zakázku s platebními identifikátory; Payment Service obsluhuje on-chain platbu. MIP-003 není náhradou A2A ani samotným GrokBot runtime. Potřebné části provozovat přes dostupnou Payment Service; volitelný registry discovery Masumi nenahrazuje povinné discovery z Pneu 007 webu.

Masumi službu registrovat podle ověřené preprod verze. Její obchodní výstup v našem demu je zakoupená potvrzená rezervace fiktivní služby. Masumi job může dokončit dodání tohoto potvrzení; netvrdí tím, že proběhla fyzická práce na autě. Výsledek musí obsahovat booking/order ID a termín, cenový režim, uhrazenou část, zbytek a platební stav.

Kontrakt a skutečný provider stav

Naše seller služba implementuje MIP-003 POST /start_job, GET /status?job_id=…, GET /availability a GET /input_schema. Vstup je konkrétní objednávka a již schválená nabídka; server znovu ověří cenu/mandát, neakceptuje klientem napsanou slevu. Payment intent uchová job ID, blockchainIdentifier, kupujícího, prodejce, neměnný input hash, asset/amounts a provider deadlines.

Ověřený pracovní API snapshot: masumi-payment-service@5fccf58b0f30873085b59ee540c67b4ae8433cd0, base <node>/api/v1, serverový header token, network="Preprod" a paymentType="Web3CardanoV1". Připojit tenkým HTTP adaptérem přes nativní fetch. Nasazenou verzi ověřit v GP; při jiné verzi znovu ověřit schéma. Zdroje: pinned Payment Service OpenAPI a seller API implementace.

Izolaci buyer/seller oprávnění ověřit na nasazené node; pokud klíč není dostatečně omezený, před ním zůstává allowlisted broker vynucující mandát a autorizované zdroje.

HTTP 200 ani NextAction nedokládají platbu. Funding je onChainState=FundsLocked s potvrzenou transaction evidence; ResultSubmitted je oddělená fáze. Seller payout vyžaduje onChainState=Withdrawn a ověřené částky/unit v poli WithdrawnForSeller; vrácení buyerovi onChainState=RefundWithdrawn a odpovídající částky v WithdrawnForBuyer. Tato dvě pole jsou seznamy částek, nikoli další názvy stavů. Pokud daná API odpověď obsahuje CurrentTransaction.status, rozlišuje Pending/Confirmed/FailedViaTimeout/RolledBack; resolve odpověď může vracet jen txHash, proto adapter nesmí předpokládat totožný tvar všech metod. Mapování a důkaz finality se testují proti pinned schématu i nasazené službě. Úspěšná rezervace s funding může být dříve než payout; UI uvádí „prostředky v escrow“ a později „vyplaceno prodejci“.

Kalkulátor podporuje všech 480 konfigurací, ale pro P0 plná on-chain úhrada nabízí pouze předem ověřené SKU; ostatní mohou využít ověřenou fixní zálohu. Plný agentí nákup potřebuje mandát payment_mode=full, celkový limit 2 300 Kč a samostatný schválený limit asset quantity/fee. Při změně assetu, provideru, mapping verze nebo částky nad limit se vyžádá zákazník. Recommend režim nerezervuje, nefinancuje escrow a nezaplatí. Lidský checkout místo agentího mandátu používá uložené autentizované potvrzení konkrétního nákupu.

Dvě autorizační cesty, jeden platební backend

Human checkout: zákazník v autentizovaném lidském zobrazení potvrdí neměnnou nabídku, slot, deposit/full, seller, síť, asset quantity, mapping verzi a fee cap. Server uloží HumanCheckoutAuthorization vázanou na tuto objednávku/verzi. Zákazník nemůže obejít cenový systém ani zaměstnanecké slevové pravomoci. Tento průchod funguje s prázdným agentím rulebookem a vypnutým relay.

Agent checkout: navíc vyžaduje účast v agentím případu, aktivní lidsky schválený rulebook, schválený zákaznický mandát a potřebné cenové výjimky. Autorizační větev odvozuje server z identity a uloženého schválení; parametr mode=human, obsah zprávy ani volání lidské URL ji agentovi neudělí. Botí identita nesmí vytvářet HumanCheckoutAuthorization. Obě cesty používají stejné hold/intent/provider/reconciliation operace.

Trvalé workflow místo předstírané společné transakce

  1. Validace: serverově odvozená identita a příslušná human/agent autorizace popsaná výše, přesná nabídka a schválení cenové výjimky, cena, slot a všechny platební limity. Agentická větev navíc ověří případ, aktivní rulebook a schválený mandát. Změnitelná pravidla se ověří před vznikem závazku.
  2. Blokace: v lokální DB transakci vytvořit unikátní objednávku/payment intent a dočasný hold na slot. Dva klienti nevlastní stejnou kapacitu. TTL není slepě fixní: musí respektovat otestované payByTime a provider finalitu.
  3. Zahájení: vytvořit Masumi job/purchase; korelační ID jsou uložená ještě před opakovatelným síťovým krokem. Při timeoutu se nejprve dohledá existující výsledek; purchase se slepě neposílá znovu.
  4. Funding: čekat na ověřený Masumi stav financovaného escrow. Teprve pak v lokální DB převést hold na potvrzený booking a zapsat kalendář/ledger event. Potvrdit lze jednou.
  5. Dodání a settlement: odevzdat hash skutečného potvrzení rezervace, sledovat potřebné provider kroky a termíny, později ověřit payout. Zákazník vidí rezervaci a oddělený stav platby; výsledek neoznačuje auto za přezuté.
  6. Neúspěch a obnova: nepotvrzená expirovaná platba vede k uvolnění hold; pozdní funding nebo nemožnost dodat booking vede ke stavu reconciliation/refund a trvalému incidentu. Neznámý funding se automaticky nemaže. Reconciliation worker po restartu načte intent a provider stav.

Refund je samostatná Masumi operace s vlastní autorizací a potvrzením; tlačítko nesmí ihned označit prostředky za vrácené. Hold/retry/refund mají auditní události. DB rollback nevrací blockchainovou transakci. Při neověřeném stavu bot nepředstírá úspěch a může požádat majitele o řešení incidentu.

Platební brána GP před hlavním demem

B a C v první integrační hodině zahájí kontrolu dostupné Masumi Payment Service, preprod key, dvou identit, test-ADA funding, registry SKU a API snapshotu. První testovací rezervace má stabilní nonce a explicitní deadlines; pracovní příklad je payBy T+20 min, submit T+60, unlock T+90 a dispute T+120. Seller API v tomto snapshotu používá ISO deadline vstupy, buyer API přesné vrácené milisekundové stringy; MIP-003 timestamp adaptér musí převést jednotky podle specifikace a round-trip testu, ne kopírovat čísla naslepo.

Na této rezervaci ověřit funding → lokální order/calendar potvrzení → skutečný voucher hash → submit-result → pozdější payout. Konkrétní snapshot vyžaduje minimální časové rozestupy a výchozí node čeká na více potvrzení a periodické zpracování; funding/settlement prodlevy změřit. Úplný payout se neslibuje během dvouminutového videa. GP se zahájí brzy, payout/refund observace mohou pokračovat později při další práci. Video ukáže skutečný stav k danému okamžiku; případný záběr pozdějšího payout má timestamp. Zdroje: výchozí konfigurace node a výše uvedená API implementace.

Druhý samostatný live smoke ověří refund request před unlock, seller autorizaci a potvrzený refund; recovery test restartuje reconciler po purchase a dohledá původní ID bez nové platby. Zaznamenat provider ID, hashe, raw stavy, verzi a prodlevy. Chybějící externí prostředky znamenají BLOCKED pro live test; lokální simulace jej nenahradí. Hold expiry musí umožnit funding confirmation po payByTime; nejasný nebo pozdně financovaný intent se nejprve vyřeší přes provider/reconciliation, ne automatickým přidělením stejného slotu jinému zákazníkovi.

Reset může resetovat jen lokální fixture data. Preprod záznamy, prostředky a pending workflow se nemažou; nový běh dostane nové session ID a stále lze dohledat předchozí transakce. Nefundovat mainnet ani kupovat skutečné assety pro fiktivní demo.

Primární technické zdroje: Masumi Node — provoz a potřebná infrastruktura; MIP-003 — kontrakt služby; Masumi agent docs hub a pinned Payment Service OpenAPI. Přesné request/response schéma a limity se ověří na skutečně nasazené verzi, ne pouze z obecného collaboration návodu.

P8 · Dva skutečné nákupní průchody

Všichni; závislost P4–P7. Pro základní průchod platí zdrojové částky: 2 472 Kč → 5% cena nad limitem → lidská 10% výjimka → 2 224,80 Kč, záloha 500 Kč, doplatek 1 724,80 Kč. Akceptace: žádné ruční kopírování zpráv, skutečný funding hash a uložený booking; customer rozliší escrow a payout. Recommend nedělá purchase. Nový plný mandát není implicitně odvozen ze starého zálohového.

P9 · Izolace, chyby, opakovatelnost a evidence

B + C testy, A důkazy. Provést T01–T25 s explicitně upravenými platebními očekáváními plus B01–B07/A01–A04/M01–M08 z §8. Zvlášť otestovat crash/timeout, hold conflict, pozdní funding, refund, seed vs on-chain historii a dvě identity. Backendový B klient není druhý skutečný GrokBot.

Akceptace: funkční legacy web/backend s dummy daty a preprod integrací, doložený audit a rulebook, skutečný agentický nákup, 2minutové video, status každého testu a limitations. Nedoložená externí integrace je BLOCKED, nikoli PASS.

10. Předání a definice „plně funguje“

  1. Legacy aplikace: vlastní web, order flow a zaměstnanecká administrace, backend API, SQLite migrace, seed, kalendář a ICS; obyčejný zákazník službu skutečně objedná.
  2. Dummy business a partneři: konzistentní historie, čtyři webové zdroje, tři interní dokumenty, source manifest, dva funkční mock supply kanály a datové exporty.
  3. Auditní průchod: skutečný GrokBot načte běžící systém, vytvoří profile/findings/rulebook s citacemi, majitel aktivuje verzi a export SKILL.md je ověřený klientem. Přiložit zdrojový change test.
  4. Masumi: pinned adapter, restricted payment broker, job/purchase/funding/result/payout/receipt workflow a live Preprod důkaz. Demo-only provider je označený a nestačí pro platební akceptaci.
  5. Handle: dvě skutečné GrokBot identity a discovery z webu; agentí nákup v mezích pravidel/mandátu přes stejný legacy backend.
  6. Důkazy a provoz: docs/legacy-runbook.html, docs/acceptance-results.html, docs/audit-evidence.html, docs/masumi-proof.html, docs/runtime-proof.html, docs/limitations.html, reset/start instrukce a 2minutové video.
Hlavní demonstrační řetězec: funkční legacy Pneu 007 → načtení webu a interních zdrojů → audit s nálezy → návrh rulebooku → lidská aktivace → živé bot discovery a jednání → autorizovaný Masumi purchase → ověřená rezervace v kalendáři a platební výsledek. Každý krok má dohledatelný zdroj nebo uloženou událost.

„Plně funguje“ znamená dokončené UI → API → DB → calendar → provider → potvrzení a obnovitelné chybové stavy. Nestačí nakreslená administrativa, dummy JSON bez zapisovatelného backendu, předem napsaný audit nebo purchase požadavek bez potvrzeného funding. Fiktivní je firma, data, fyzická služba a ekonomický význam testnet částek; kód, audit, dialog, kalendářové zápisy a Preprod transakce mají být skutečné.
