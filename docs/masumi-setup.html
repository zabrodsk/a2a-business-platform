Update 9 October 2026: Blockfrost access, free wallet funding, service registration, buyer escrow funding and the reservation receipt's on-chain hash are verified. The same booking/payment identities survived application and node restarts, with exactly one booking, payment and intent. Seller collection is confirmed and the deployed application records seller_paid from independently verified chain inputs and outputs. These are test tokens with no monetary value. Current evidence · English operating guide.

The pinned node's bundled Mesh SDK had stale Cardano transaction cost models. Runtime files under infra/masumi/runtime backport Masumi's official synchronization fix from commit d569a338ca54d5be7441564770d75ebf89b71f12; all four compiled SDK builder constructions use current chain models and protocol parameters. Both nodes run in production mode to retain upstream error redaction. The registry request was retried only after a deterministic rejected submission with no chain transaction; its failed attempt was preserved privately. Registration then confirmed.

The application can reach the nodes through an authenticated allowlisted gateway bound locally to port 8811, published by the existing Tailscale installation on HTTPS port 10000. Privileged node management routes are not forwarded. This uses the existing Mac mini rather than additional paid cloud services. The gateway runs as a launch agent.

The optional server setting MASUMI_TIMING_PROFILE=preprod_smoke uses deadlines at 5/16/32/48 minutes (payment/result/unlock/external dispute), satisfying pinned minimum gaps. This pinned node additionally waits 10 minutes after unlock before automatic collection, so collection starts around minute 42 plus confirmation time. The default profile remains 20/60/90/120 minutes. The controlled buyer started with 20 test-ADA; the deposit is 5 test-ADA and MASUMI_CHECKOUT_NETWORK_FEE=15000000 explicitly exposes a maximum additional 15 test-ADA budget. That budget is not the actual fee. The UI displays and submits the same budget for human approval; approved agent mandates retain their own limits.

Both local Masumi APIs are running with funded Preprod wallets, verified Blockfrost access and a confirmed deposit SKU registration. Secrets remain in private environment files. The controlled smoke run has confirmed funding, result and seller collection transactions. A customer seller-job payload is {"input_data":{"order_id":"ACCEPTED_ORDER_ID"},"identifier_from_purchaser":"0123456789abcdef0123"}. It requires the existing accepted order and approved mandate. Purchaser identifiers must be even-length lowercase hex with 14–26 characters; retries keep the same nonce and order. Start returns the normative MIP-003 id, camelCase payment fields and second-based deadlines. Job preparation creates no buyer charge. Use the existing configured buyer workflow to fund that signed payment; buyer node deadlines remain milliseconds.

Input hashing now follows MIP-004: SHA-256 of purchaser identifier, semicolon and canonical input JSON. The supported input has exactly one string field, order_id, so its JSON serialization is canonical. Output hashing uses the purchaser identifier, semicolon and the exact persisted receipt string returned as result. Status also returns input_hash and output_hash. Submit the 64-character output hash; the input hash is stored separately.

The Masumi guide links examples that differ from the formal MIP-003 contract. The guide's concatenated input/output submission also differs from the official SDK's output-only submission. This implementation preserves the formal API and raw-string MIP-004 hashing. That SDK version JSON-escapes output before hashing, which differs for JSON receipts; validate this explicitly when integrating such a buyer. Existing persisted intents keep their original hashes and require reconciliation if created under an earlier scheme.

Funding a registrace: potvrzené na Preprod. Lokální seller a buyer Masumi API, dvě databáze a čtyři peněženky fungují. Nákup jobu, odevzdání výsledku a výplata prodejci se ověřují samostatně. Masumi nikdy tiše nepřepíná do lokální simulace. Lokální režim má provider local_demo, síť local a identifikátory demo:.

1. Ověřená verze a infrastruktura

Kontrakt je připnut na commit 5fccf58b0f30873085b59ee540c67b4ae8433cd0. Compose sestavuje oficiální Dockerfile z přesně tohoto commitu; nepřidává žádné aplikační SDK. Dva Payment Service nody oddělují seller a buyer credentials a peněženky. Každý používá vlastní PostgreSQL 15. Přístupy z hostitele jsou pouze localhost, porty 3001 a 3002.

Před buildem spusť read-only kontrolu zdrojů:

node infra/masumi/verify-upstream.mjs

Na tomto hostiteli je ověřen Compose příkaz docker-compose (5.1.4); plugin docker compose není dostupný. Použij docker-compose v níže uvedených příkazech. Dvě databáze i dva API kontejnery jsou spuštěné. Oficiální plný Docker build skončil SIGKILL při sestavení admin frontendu: Docker zde má přidělené přibližně 2 GB RAM. Compose proto používá původní upstream target backend-builder a spouští API přes připnutý runtime bootstrap. API a Swagger fungují; grafický admin dashboard v tomto image není sestavený. Jde o lokální provozní volbu, nikoli požadavek protokolu.

Kontrola stahuje pouze čtyři soubory, porovnává SHA-256 a neprovádí upstream kód. PostgreSQL postgres:15-alpine je spuštěný pro oba nody; ověřený digest je sha256:f7d23353e1b15400d22ebe31189f4d314b87a4c129cc400c8c2d8d4ca127bf81.

Pokračování lokálního setupu: vlož vlastní Blockfrost Preprod projektový klíč do BLOCKFROST_API_KEY_PREPROD v infra/masumi/.env, potom spusť node infra/masumi/provision.mjs. Skript znovu použije vytvořené peněženky a aplikační klíče, připojí Blockfrost a aktualizuje privátní aplikační env. Bez klíče umí připravit offline peněženky, ale neumí ověřit blockchain. Veřejné údaje o lokálním setupu jsou v data/masumi-node-setup.json; žádná přístupová tajemství tam nejsou.

Oficiální dokumentace nabízí také Masumi as a Service na app.masumi.network. Blockfrost účet je vstup pro zvolenou self-hosted cestu; není univerzální podmínkou všech způsobů použití Masumi. Hosted cesta spravuje infrastrukturu a vyžaduje vlastní přihlášení, organizaci a případné ověření identity. Tento projekt nyní používá oddělené vlastní seller/buyer nody.

4. Aplikační nastavení a poplatkový limit

Serverové env podle infra/masumi/app.env.example. Zvolený provider masumi bez vstupů vrací MASUMI_NOT_CONFIGURED. Úspěšně nakonfigurovaný provider také vyžaduje oddělený fee budget; příklad klíčů nikdy neobsahuje actual secret.

Vzdálené API vyžaduje HTTPS. HTTP je povolené jen s výslovným MASUMI_ALLOW_LOCAL_HTTP=true a hostem localhost, 127.0.0.1 nebo [::1], například porty 3001/3002 mapované v Compose. Buyer i seller URL podléhají stejné kontrole; redirects jsou zakázané.

Pinned purchase API nemá parametr maxFee. Adapter proto nedeklaruje nativní fee enforcement. Bez ověřené izolované peněženky vrací MASUMI_FEE_CAP_NOT_ENFORCED. Při explicitním MASUMI_DEDICATED_BUYER_WALLET=true a buyer address ověřuje skutečné GET /payment-source/, jedinou purchasing wallet a všechny dostupné UTXOs. Její aktuální balance musí být alespoň SKU price a nejvýše price + schválené max_network_fee.

Externí lifecycle fence je GP / NOT_RUN: buyer node i peněženka smí být použity jen pro jediný serializovaný purchase workflow. Během celého lifecycle nesmí jiný klient, proces či top-up zvýšit balance nebo spustit další výdaj. Nastavení MASUMI_BUYER_LIFECYCLE_ISOLATED=true je výslovné prohlášení operátora, že tyto podmínky externě zajišťuje; samo je nevynucuje ani neprokazuje. Bez něj adapter purchase odmítne. Jedna instance provideru navíc drží zámek pro intent až do potvrzeného payoutu/refundu, včetně timeoutu; po restartu jsou nadále nutné persistentní aplikační fence a provozní kontrola.

HTTP fixtures prokazují kontrolu source/wallet/quantity a interní zámek, nikoli zákaz externího financování, reálnou chain transakci nebo miner fee cap. Živý Preprod běh ověřil tento konkrétní node, funding, receipt a collection; důkazy jsou v samostatném reportu. Veřejný status rozlišuje purchase_configuration_complete od purchase_ready. První skutečný test lze spustit teprve po kompletní konfiguraci a výslovném MASUMI_ENABLE_PREPROD_PURCHASES=true; potom purchase_ready=true znamená pouze operator_preprod_test_enabled_not_verified. Stav ověření zůstává live_verification=NOT_RUN, důvod LIVE_SMOKE_TEST_REQUIRED. Default flag je false a adapter vrací MASUMI_PREPROD_PURCHASES_DISABLED před jakýmkoli API voláním. Pokud provozní podmínky nejsou zajištěny, nech isolation i enable flags false. Balance ceiling omezuje veškeré další výdaje, nikoli pouze miner fee.

Final seller verification additionally uses the private MASUMI_BLOCKFROST_PROJECT_ID and optional explicit MASUMI_COLLECTION_ADDRESS. Normal Withdrawn payments have empty WithdrawnForSeller in both pinned and current official source; those arrays describe disputed allocation. The adapter instead verifies the confirmed transaction consumes the original result escrow and creates the expected collection output, excluding collateral and returned change. 5. Stavový kontrakt a časování

Payment creation přijímá ISO deadlines, vrací millisecond stringy. Buyer API této verze očekává stejné millisecond stringy; nedělit je 1000. NextAction je fronta práce, nikoli potvrzení blockchainu. Rozhodující je onChainState a potvrzený txHash. Výsledek se SHA-256 je digitální rezervace/voucher; fyzické přezutí má samostatný stav.

provider_payment_id je skutečné buyer purchase ID a není přítomné před ověřením buyer odpovědi. Samostatné seller_payment_id identifikuje seller payment request. Intent ID nikdy nenahrazuje blockchainové či provider ID. Po timeoutu buyer může existovat pouze seller ID; pozdější ověření doplní stabilní skutečné buyer ID.

Lokální stavMasumi evidence
purchase_requestedNextAction FundsLockingRequested/Initiated; ještě nejde o funding
escrow_fundedonChainState FundsLocked + potvrzená transakce; teprve teď potvrdit booking
result_submittedResultSubmitted; delivered voucher hash
seller_paidWithdrawn + aktuální potvrzená transakce + nezávislé Blockfrost ověření spotřebovaného result escrow a přesného collection výstupu
refund_requestedRefundRequested; stále nejde o vrácení peněz
refundedRefundWithdrawn + WithdrawnForBuyer
reconciliation_requiredTransport uncertain, rollback, sporná platba nebo chybějící identity/proof

Adapter volí payBy T+20 min, submit T+60, unlock T+90, external dispute T+120. Pinned validace vyžaduje submit nejméně 15 minut do budoucna, unlock dalších 15 minut a external dispute dalších 15. Node default má periodické úlohy po několika minutách a 20 potvrzení. Payout nelze garantovat během pětiminutové prezentace.

6. První skutečný smoke test a recovery

  1. Ověřit health, Preprod payment sources, fixed metadata, buyer wallet funding/collateral a dostupné SKU. Uložit použitou verzi a veřejný funding proof.
  2. Vytvořit objednávku s buyer mandátem, quantity, max fee, quote version a dostatečně dlouhým holdem. Persistovat intent ještě před provider start.
  3. Seller POST /payment/; buyer POST /purchase/. HTTP 200 znamená jen queued purchase. Pollovat resolve-blockchain-identifier a potvrdit FundsLocked se správnou identity a částkou.
  4. V lokální DB atomicky potvrdit order + calendar event, vytvořit voucher; serverový outbox spustí POST /payment/submit-result se skutečným SHA-256 uloženého výsledku.
  5. Po unlock a cron zpracování ověřit Withdrawn a skutečný net payout. Uložit txHash, provider id, network a pozorovaný raw proof bez credentials.
  6. Volitelný samostatný refund test (v tomto běhu nebyl proveden): po skutečném funding požádat buyer POST /purchase/request-refund před unlock; autorizaci provede owner v seller workflow POST /payment/authorize-refund. Adapter zákaznického requestRefund nikdy automaticky refund neautorizuje. Ověřit RefundWithdrawn a vrácenou částku.
  7. Přerušit klienta po odeslání purchase, obnovit persistent workflow a resolve stejný blockchainIdentifier. Žádná druhá platba, žádný druhý booking. Při ztraceném seller response použít lookup podle metadata intent; observe nikdy sama nevytvoří nový payment.

DB a blockchain nejsou jedna atomická transakce. Žádný timeout se nesmí převést na „nezaplaceno“, uvolnění holdu či nové inkaso bez reconciliation. Po seller payout nelze slibovat escrow refund; případná kompenzace je jiný owner proces.

Výslovné owner recovery: resumePurchase(request, previous) řeší existující seller request, pro který první buyer purchase nebyla odeslána nebo její odpověď chybí. Nejprve ověří uloženou identity, autoritativní seller záznam, původní deadline a buyer lookup. Pokud buyer purchase existuje, vrátí jeho důkaz; jinak odešle stejné původní signed blockchainIdentifier přes běžné opt-in, fixed SKU a budget kontroly. Nevytváří nový seller request ani nonce. Background polling tuto operaci nevolá. Deduplication konkrétní připnuté node verze tvoří lookup guard v purchase handleru a databázová UNIQUE constraint na PurchaseRequest.blockchainIdentifier; při změně verze či databáze je nutné toto znovu ověřit. Nejasná či zmizelá seller identity zůstává blokovaná.

authorizeRefund(request, previous) je samostatná owner operace s seller credentials a vyžaduje nejprve skutečně pozorovaný buyer RefundRequested. Samotný zákaznický requestRefund ji nikdy nevolá. Úspěšná autorizace ani HTTP 200 ještě nejsou důkazem refund withdrawal.

MIP-003 seller příprava: prepareJob(request) použije persistovanou quote/mandate-bound objednávku a vytvoří nebo dohledá pouze seller payment request. Nikdy nevolá buyer API ani nepodepisuje buyer purchase. Vrací application job ID intentu, skutečné signed blockchainIdentifier, agentIdentifier, sellerVKey, purchaser nonce, input hash a deadlines v unixových sekundách. Zdrojové ms stringy se nejprve validují a až potom dělí 1000; samotný purchase adapter nadále předává původní ms hodnoty. Seller timeout je výslovná chyba MASUMI_TRANSPORT_UNCERTAIN, nikoli náhradní job či chain ID. Lokální prepareJob vrací simulation=true a identifikátory demo:; router jej nesmí označit jako dostupnou Masumi službu.
