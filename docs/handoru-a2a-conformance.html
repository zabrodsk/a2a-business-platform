Credential adapter used for the TCK

This pinned TCK checkout documents bearer environment configuration but its current JSON-RPC client and direct HTTP tests do not load that configuration. A separate pytest fixture supplied the scoped synthetic customer header only to the exact relay origin and endpoint. It left explicit credentials, payloads and assertions unchanged. Separate requests without this adapter proved the relay rejects missing or invalid credentials. The adapter does not establish an end-user credential acquisition flow.

Credentials were held in a mode 0600 file outside Git and were absent from the published card, reports and console output. Downloaded evidence is redacted. The Inspector server log was also checked and contained neither test credential.

python run_tck.py --sut-host <website-origin> --transport jsonrpc -- -p handoru_auth_plugin --disable-warnings

The private fixture path was passed through HANDORU_CONFORMANCE_STATE, with the deployment adapter supplied by PYTHONPATH. The official runner generated compatibility JSON/HTML, JUnit and pytest HTML reports.

Remaining failed tests

TestFileArtifact / TestFileUrlArtifactThe official scenarios expect a raw-file or URL-file artifact named output.txt. The current business responder and private reply tools do not implement these scenario modes.
TestDataArtifactThe scenario expects a specific data object as the first artifact part. The scripted responder returned a text part.
TestMessageResponseThe scenario expects a direct Message result. This relay returns a Task for its persistent conversation workflow. The corresponding specialized fixture mode is not implemented.
TestAgentCardLastModifiedLast-Modified is absent. The official requirement CARD-CACHE-003 is MAY; this test asserts it unconditionally. ETag and mandatory revalidation are present.

These six failures remain in the attached full official report. They are not reclassified as passes. Many skipped cases cover undeclared transports or optional capabilities; skipped cases do not prove those features work. Protocol issue found and corrected

The first authenticated full run exposed two failures: push-notification creation returned an invalid-parameters error after URL validation even though the card declared push unsupported. The application now rejects the unsupported capability first, using the standard PushNotificationNotSupportedError. After restarting the isolated application and rerunning the same official suite, both tests passed. Streaming and push flags remain false.

Inspector method

The unmodified official Inspector backend was started with its built frontend. A Socket.IO client exercised the actual card-fetch, initialize-client and send-message handlers. It discovered the relay through the business website, used its own scoped test credential and received one completed task. This is live interoperability with the Inspector and Python SDK; it is not a screenshot review, a second customer GrokBot or unattended runtime evidence.
