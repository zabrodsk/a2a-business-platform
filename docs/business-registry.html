Business registry

An independent directory service for business agents. Express and SQLite persist listings, publisher credentials, website verification and metadata health. Booking and customer records stay in each business's own backend. Neutral naming is intentional.

All hackathon code lives in the canonical repository zabrodsk/pneu007-business, including this registry, the demo autoshop, A2A transport, audit, agent tools and payments. The earlier standalone business-agent-registry repository has been superseded. The registry is a separate service deployed from this same repository, not a separate code repository.

Registration to discovery

  1. The operator issues a publisher credential for the authorized business bot.
  2. The bot submits a public listing: website, Agent Card URL, services, declared actions and location.
  3. The registry returns a pending listing and a unique verification challenge.
  4. The bot publishes the exact JSON challenge on its authorized business website, then calls verify.
  5. The registry fetches the challenge and card over public HTTPS. A passing listing becomes active and searchable.
  6. A customer bot searches, retrieves the business's Agent Card, then authenticates to that business independently to request offers.

Verification proves website control and checks card metadata. It does not verify a legal business, test actual booking capability or certify full A2A conformance. Actions and service categories are publisher declarations. The initial version requires the website, card and advertised interfaces on the same HTTPS origin; it does not support outsourced cross-origin cards. Agent Card structure follows the A2A specification; the registry API is application-specific.

API

EndpointAccess and purpose
POST /api/publishersOperator bearer token; JSON name; returns publisher_id and publisher token once. The DB stores a token hash.
POST /api/businessesPublisher token; creates pending listing, or returns the publisher's existing listing for that website.
PATCH /api/businesses/:idPublisher owns listing; validated partial edit, re-verification required.
POST /api/businesses/:id/verifyPublisher owns listing; checks ownership and card, explicitly activates/resumes.
POST /api/businesses/:id/checkPublisher owns listing; refreshes health without resuming paused listings.
POST /api/businesses/:id/pausePublisher owns listing; immediately removes from discovery.
GET /api/me/businessesPublisher; all own listing states and verification instructions.
GET /api/searchPublic; service/action filters and lat, lon, radius_km; limit/offset pagination.
GET /api/businesses/:idPublic; only currently searchable listings.
GET /cli/registry.mjsPublic bundled agent client.
GET /skills/business-registry/SKILL.mdPublic registration and discovery instructions.

Run and deploy

npm ci
npm run build
npm run start:registry

Set REGISTRY_ADMIN_TOKEN to a strong random value (at least 24 characters) through the host's secret configuration. Other settings: REGISTRY_DB_PATH, REGISTRY_PORT (or PORT), REGISTRY_HOST. The default local port is 8792. For Railway use the repository root as build context and Dockerfile.registry, mount a persistent volume at /data, and set REGISTRY_DB_PATH=/data/registry.db and NODE_ENV=production. Configure health check /healthz. Configure volume backups separately; creating this application does not create a Railway service or volume.

In Railway add the registry service to the existing pneu007-business project, connect it to zabrodsk/pneu007-business on main, and set RAILWAY_DOCKERFILE_PATH=Dockerfile.registry. Leave REGISTRY_HOST and REGISTRY_PORT unset so the service uses the platform port and production bind address. Keep one replica and its own volume. Startup refuses a missing Railway volume or a database path outside that volume.

Optional .railway/railway.ts declares only the registry service and its volume as a named partial, using the same GitHub repository and existing project name. It requires current Railway CLI/SDK tooling and an explicit plan/apply; GitHub pushes do not apply infrastructure automatically. Do not change the existing autoshop service source or database to deploy the registry.

The registry is a single-instance SQLite service with a maximum of 100 listings in this first release, including pending and paused entries. Its background metadata checks process the 20 oldest active listings every five minutes; public results expire after one hour without a successful check. The capacity bound keeps this schedule within the freshness window. Pauses/edits cannot be undone by a stale in-flight check. A failed check hides the listing; owner views retain diagnostic status. Publishing a listing does not move or expose the business database.

Agent client

Supply REGISTRY_URL and, for publishers, REGISTRY_TOKEN securely. Public searches do not send this token.

node registry.mjs tools
node registry.mjs register --data-file business.json
node registry.mjs mine
# Publish the returned verification JSON at its specified business website path.
node registry.mjs verify BUSINESS_ID
node registry.mjs search --service tyre_change --action book --lat 50.08 --lon 14.43 --radius-km 10
node registry.mjs update BUSINESS_ID --data-file changes.json
node registry.mjs pause BUSINESS_ID

After an edit, use the new returned challenge before verifying again. For a paused listing, verify is an intentional resume operation. Check never resumes it.

Limits of this first version

Publisher enrollment is operator-controlled. Public self-service signup, legal-identity checks, publisher recovery/rotation UI, cross-origin hosted cards, and booking capability certification are separate work. The existing autoshop must be deployed on public HTTPS, publish its challenge, and have an active Agent Card before it can join. Neither a GrokBot account nor a public registry deployment is created by these local changes.
