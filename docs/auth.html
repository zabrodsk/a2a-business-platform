Agent identity and auth.md

The demo business implements a local customer-linking flow described by /auth.md, using its existing customer login. No external WorkOS account or subscription is required. Each registration receives a stable agent identity. It gains customer access only after that customer signs in and confirms a short-lived code. The business records the acting agent separately from the customer it represents.

Deployed on the Pneu 007 demo. The actual customer and business GrokBot test records the live consent, negotiation and booking results. The registry service and standalone relay keep their existing enrollment mechanisms. Provider-verified ID-JAG assertions and provider Security Event Tokens are not supported or advertised.

Discovery and registration

EndpointPurpose
GET /auth.mdRuntime instructions for registering, claiming, exchanging and revoking credentials.
GET /.well-known/oauth-protected-resourceResource metadata pointing to the authorization server. Protected API and A2A 401 responses include this discovery URL.
GET /.well-known/oauth-authorization-serverSupported grants, scopes and agent registration endpoints.
POST /agent/identityJSON {"type":"anonymous"} creates an unclaimed agent and returns a signed identity assertion. JSON {"type":"service_auth","login_hint":"customer@example.com"} starts customer confirmation and returns no assertion before confirmation.
POST /agent/identity/claimAn anonymous agent starts customer linking with its claim_token and the customer's email. Email supplied by the agent is a hint, not identity proof.
POST /oauth2/tokenForm-encoded JWT-bearer exchange or claim polling. Returns an opaque Bearer access token and a replacement signed assertion. Retain the replacement: assertions are single-use.
POST /oauth2/revokeForm-encoded token revokes one access token. To end the delegation and prevent further exchanges, the customer revokes the registration in the portal.

Customer linking

  1. The agent shows its registration ID, the six-digit user_code and the service's verification_uri to the customer.
  2. The customer opens that link, signs in with the existing customer login, checks the agent identity and enters the code.
  3. The server matches the signed-in customer's account email, binds the agent to that customer and invalidates all pre-claim credentials.
  4. The agent polls the token endpoint with grant_type=urn:workos:agent-auth:grant-type:claim and its claim_token, respecting the advertised interval.
  5. The resulting Bearer credential works for both A2A and customer tools. Store credentials privately; use the existing A2A client's login stdin input and the garage client's private credential configuration. Never paste access tokens, assertions, passwords or session cookies into a conversation.

Only the matching signed-in human customer can confirm. Agent tokens, business agents and owner agents cannot perform this step. The link cannot be moved to another customer. At /agent/access, the customer can inspect and revoke their registrations.

Identity and authority

GET /api/agent/identity returns agent: {id, role} and acting_for: {type: "customer", id}, or null before linking. This proves a local account association, not the identity of a real-world person or a particular agent provider. Existing configured business and owner agents retain their identities; they do not acquire a customer binding.

Unclaimed credentials have only agent.identity scope. Linked credentials additionally have a2a and customer.tools, enforced by the existing authenticated roles and customer ownership checks. Agents cannot request wider scopes. Business inbox items include a server-written customer_identity snapshot with both the agent ID and customer ID. Text and metadata in messages cannot override it.

Customer linking grants access to the negotiation workflow. It does not approve a mandate, expand a spending limit, activate a business rulebook, approve a discount exception or initiate an otherwise unauthorized purchase. Existing human and business policy checks remain authoritative.

Credential lifecycle

Access tokens expire within one hour; replacement assertions last up to 24 hours and must be exchanged before expiry. Unclaimed registrations expire after 24 hours and claimed registrations after 30 days. Claim codes expire within ten minutes, allow five wrong submissions and require polling no faster than every five seconds. Tokens, claim handles and codes are stored as hashes. Assertions use a persisted Ed25519 signing key, audience and expiry validation, registration version checks and replay protection. The business database and its SQLite sidecar files are restricted to owner read/write permissions.

Revoking a registration disables its access tokens and future assertion exchanges in both A2A and business tools. It does not cancel a booking or undo an already authorized transaction; those use the existing cancellation and payment workflow. Restarting the application preserves registrations, keys, expiry and revocation.

Verification

Automated tests exercise discovery, anonymous restrictions, customer-only confirmation, code and session checks, account isolation, signed-assertion validation, replay, expiry, revocation and persistence. The unified system test registers and links an agent, exchanges an A2A message, opens a business case for the linked customer, verifies that forged message identity does not change the binding, and revokes access on both API surfaces.

Run npm run typecheck and npm test. The runtime report separately records actual GrokBot execution; distinct GrokBot accounts have not been verified.
