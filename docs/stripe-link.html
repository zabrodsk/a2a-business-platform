This integration accepts Stripe test payments only. It refuses live API keys. Test CZK payments and fictional reservations have no monetary value. The existing Handle / handoru.ai Stripe test account is connected. A 500 CZK payment through the actual Link wallet is verified, with one payment and booking, a processed webhook, unchanged retry identifiers and restart recovery. Runtime evidence.

Open the Link checkout flow. At order authorization, choose “Link / karta” and use the “Zaplatit přes Link / kartou” button. Configure the service and appointment, sign in as the customer, review the amount, explicitly approve it, and continue to Stripe Checkout.

What Link does

Link is Stripe's wallet for saving and reusing payment details. The website redirects to Stripe's hosted Checkout, where eligible customers can choose Link or another enabled method. A link to link.com itself does not collect a payment for the business. Enable Link in the merchant account's payment-method settings; this integration uses Stripe's recommended dynamic payment methods.

Server configuration

Store test credentials privately using infra/stripe/app.env.example as the variable-name reference. Required inputs are STRIPE_SECRET_KEY, STRIPE_ACCOUNT_ID, and this application's own STRIPE_WEBHOOK_SECRET. A hosted Checkout does not need a browser publishable key. Every API request is scoped to the configured Stripe account; a scoped Checkout read verifies access before an appointment hold is created. The runtime restricted key needs Checkout Sessions read/write and PaymentIntents read. Webhook Endpoints write is needed to register this application’s endpoint, and can be removed after setup. Missing credentials leave Link unavailable; configuration alone is not payment evidence.

Register https://pneu007-production.up.railway.app/api/stripe/webhook in the same Stripe test account, with these events: checkout.session.completed, checkout.session.async_payment_succeeded, checkout.session.async_payment_failed, and checkout.session.expired. The endpoint verifies the signature on the unchanged request body. It retrieves the current Session using its server key; a redirect or client-supplied “success” cannot confirm a booking.

Recovery behavior

One order can use one provider. The backend persists the approved quote, amount, merchant identity, request parameters and idempotency key before creating Checkout. Interrupted requests reuse those identifiers. Stripe holds have a 31-minute Session deadline, satisfying Stripe's 30-minute minimum. Dispatched or uncertain holds remain protected until authoritative provider evidence resolves them. Untouched preparations can safely expire without a provider call.

Confirmed asynchronous failure requires the signed failure event plus the matching completed/unpaid Session and PaymentIntent showing zero received funds and a payment error. It releases the hold without using Stripe's unsupported direct cancellation of Checkout payment intents. If later payment evidence arrives after release, the application records funds and requests reconciliation instead of silently booking the appointment.

Automated Stripe refunds and cancellation of an active Stripe checkout are outside this addition. Active or paid Stripe orders require an operator to resolve the provider payment before cancellation/reset; they cannot be treated as unpaid. Refresh the existing order after an interruption rather than creating another purchase.

Verification

Domain, adapter and HTTP tests cover human approval, ownership, exact server amounts, signed webhook tampering, duplicate events, restart recovery, uncertain requests, cross-provider exclusion and safe failure/late-payment handling. Browser checks cover desktop/mobile layout and prevent checkout before login and approval. The live technical test used the actual Link sandbox wallet and Stripe’s official test card under an operator-controlled seeded customer session. The provider reported payment_method=link and succeeded; the deployed app confirmed the booking. This is a technical test, not an independent customer identity demonstration.
