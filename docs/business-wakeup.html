Automatic wake-up belongs in setup

The agent reuses its authorized enrollment, creates or updates its actual native webhook routine and registers its real private callback. Setup stays pending until that handler executes and acknowledges the actual one-use event. HTTP 200 or timed polling is not automatic readiness.

node inbox.mjs setup-wakeup --config-file PRIVATE_WEBHOOK.json
node inbox.mjs wakeup-status
# Native routine only, with the actual webhook body:
node inbox.mjs acknowledge-wakeup --event-file PRIVATE_EVENT.json

Use the same isolated INBOX_CONFIG on every command. Managed relay bases preserve the server-returned /relay/ID prefix; remove only the final /bot from the inbox URL. Configuration files contain {url,key}; actual webhook bodies contain setup_probe.token. Files must be private regular JSON files (mode 0600). Never send keys, event challenges or reusable credentials through chat or command arguments.

The installer yields, allowing the native routine to wake. The backend retries every fifteen seconds for up to five minutes even with no customer messages. It retains bounded challenge hashes, accepts a legitimate delayed challenge once, persists proof across restart, and binds it to the callback, credential and current managed connection. Revocation/handover or callback changes invalidate readiness. Failed deliveries automatically rearm verification; stale failures cannot overwrite a replacement hook.

The bot must handle webhook secrets privately through actual supported runtime tools, reusing authorized configuration or generating a secret when the creation tool supports it. It must never ask a person to retrieve or paste a key. If the runtime exposes only a human-only key panel and no private configuration/secure connection path, automatic setup for that runtime is not implemented. Keep setup pending and report that limitation in one short, user-facing sentence. Server deployment cannot create a routine inside another person's account by itself. A friend's already-enrolled bot must refresh the skill and finish this setup once; it must not re-enroll or create duplicate routines.

Setup does not activate rules, grant customer consent, bypass operation scopes or authorize payment. Earlier actual GrokBot tests proved native wake-up; every new routine now needs its own acknowledgment.

Published business setup skill

If the runtime hides its webhook key, the business skill now supports a persistent native recurring inbox routine. Each real scheduled execution calls inbox scheduled-check-in --interval 60, processes pending work and exits. inbox availability exposes recent authenticated check-ins after two spaced observations; the schedule remains client-reported and must be observed in the runtime. No callback key or URL is required. Stale check-ins or revoked authority remove availability. This is scheduled inbox checking, not verified webhook delivery.
